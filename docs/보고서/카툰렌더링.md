# 고정 파이프라인 기반 카툰 렌더링 기법 분석 보고서

> 분석 대상: [`tutorials/chapter7/main.cpp`](../../tutorials/chapter7/main.cpp)

## 개요

본 보고서는 셰이더를 전혀 사용하지 않고 **OpenGL 2.1 고정 기능 파이프라인(Fixed-Function Pipeline)** 만으로 카툰(Toon/Cel) 렌더링을 구현한 `chapter7/main.cpp`를 분석한다. 핵심은 프래그먼트 셰이더에서 수행할 조명 계산을 **1D 램프 텍스처 + `glTexGen` + 텍스처 환경(Texture Environment)** 으로 대체하고, 실루엣 외곽선을 **뒷면(Back-Face) 셸 렌더링**으로 만드는 두 축이다.

## 1. Diffuse·Specular의 스레숄딩화 — 카툰 렌더링의 Remap 원리

### 1.1 일반 조명과 카툰 조명의 차이

전통적인 램버트(Lambert) 확산광은 연속 함수다.

```
diffuse = max(N · L, 0)      // 0.0 ~ 1.0 사이 연속값
```

이 값을 그대로 색에 곱하면 명암이 **부드러운 그라데이션**으로 나타난다. 반면 카툰 렌더링의 목표는 이 연속값을 **몇 개의 불연속 밴드(band)** 로 계단화(quantize)하는 것이다. 즉 조명 강도라는 아날로그 신호를 "그림자 / 중간 / 하이라이트"처럼 **양자화된 색 단계**로 재사상(remap)한다.

### 1.2 이 코드의 Remap 파이프라인

이 데모는 `N·L`을 직접 계산하지 않고, **텍스처 좌표 → 램프 텍스처 룩업(LUT)** 이라는 우회로로 remap을 수행한다. 흐름은 다음과 같다.

```
정점 위치(=법선)  ──[glTexGen]──▶  s = N·L  (범위 -1..1)
                  ──[텍스처 행렬]──▶  s' = s·0.5 + 0.5  (범위 0..1)
                  ──[1D 램프 텍스처 LUT]──▶  양자화된 밝기 v
```

여기서 **실제 remap 함수(스레숄딩)** 를 담당하는 것이 `buildRamp()`의 `switch(style)` 이다. `t`는 0..1로 정규화된 조명 강도이며, 이를 밝기값 `v`로 변환한다.

**(1) 2-tone — 경계 하드 스레숄딩**

```c
case 0: /* 2-tone: hard shadow/lit split */
    v = (t < 0.45f) ? 80 : 230;
```

`t = 0.45`를 경계로 어두움(80) / 밝음(230)의 두 값만 존재한다. 이것이 가장 순수한 형태의 **스텝(step) 함수** 로, 조명이 임계값을 넘는 순간 색이 계단처럼 튄다.

**(2) 3-tone — 다단 스레숄딩**

```c
if      (t < 0.30f) v = 60;    // 그림자
else if (t < 0.60f) v = 155;   // 중간톤
else                v = 235;   // 하이라이트
```

임계값을 0.30, 0.60 두 개로 늘려 밴드를 3단계로 만든다. 여기서 최상위 밴드(235)가 **Specular 하이라이트의 역할**을 근사한다. 정통 카툰 셰이딩에서 Specular 항 역시 `specular > threshold ? 흰색 : 없음` 식으로 이진 스레숄딩되는데, 이 코드는 diffuse LUT의 최상단 밴드로 그 하이라이트 영역을 표현하고 있다.

**(3) smooth-step — 부드러운 계단**

```c
// x*x*(3-2*x) 는 표준 smoothstep 다항식
if(x<0)x=0; if(x>1)x=1; s += x*x*(3-2*x)*0.35f;
```

세 구간에서 `smoothstep(e0, e1, t)` 를 누적한다. 하드 스텝의 딱딱한 경계를 미세하게 완충해, 밴드 경계에 얇은 안티앨리어싱 같은 전이 구간을 준다. "부드러운 카툰" 느낌을 위한 것이다.

### 1.3 하드 경계를 유지하는 핵심 — NEAREST 필터

remap 결과가 계단 형태를 유지하려면 텍스처 샘플링이 밴드 사이를 보간하면 안 된다. `uploadRamp()`에서:

```c
glTexParameteri(GL_TEXTURE_1D, GL_TEXTURE_MIN_FILTER, GL_NEAREST);
glTexParameteri(GL_TEXTURE_1D, GL_TEXTURE_MAG_FILTER, GL_NEAREST);
```

`GL_NEAREST`는 가장 가까운 텍셀을 그대로 반환하므로 밴드 경계가 **날카롭게** 남는다. 만약 `GL_LINEAR`였다면 두 밴드 사이가 보간되어 그라데이션이 다시 살아나 카툰 느낌이 사라진다(주석 `NEAREST = hard band edges; LINEAR would blur them`).

> **요약:** 이 코드의 "스레숄딩"은 조명값을 텍스처 좌표로 바꾼 뒤, 계단형 룩업 테이블(램프 텍스처)로 색을 조회하고, NEAREST 필터로 그 계단을 보존하는 것이다. Diffuse는 램프의 하위~중위 밴드가, Specular 하이라이트는 최상위 밴드가 담당한다.

## 2. 고정 파이프라인에서의 카툰 텍스처 동적 생성과 Texture Blending

### 2.1 텍스처의 동적(절차적) 생성

램프 텍스처는 파일에서 읽는 것이 아니라 **CPU에서 매번 계산해 생성**한다. `uploadRamp()`:

```c
unsigned char pixels[RAMP_SIZE * 3];   // 256 x RGB, 스택 버퍼
buildRamp(pixels, style);               // 절차적으로 픽셀 채움
...
glTexImage1D(GL_TEXTURE_1D, 0, GL_RGB8, RAMP_SIZE, 0,
             GL_RGB, GL_UNSIGNED_BYTE, pixels);   // GPU 업로드
```

사용자가 `1/2/3` 키를 누르면 `keyboard()`에서 `uploadRamp(style)` 이 재호출되어 램프가 **런타임에 다시 생성·재업로드**된다. 즉 텍스처가 정적 리소스가 아니라 파라미터(스타일)에 따라 생성되는 절차적 텍스처다. 256×1 크기의 1D 텍스처라 재생성 비용도 무시할 만하다.

### 2.2 조명값을 텍스처 좌표로 — glTexGen

이 데모의 가장 영리한 부분이다. `N·L`을 셰이더로 계산하는 대신, **텍스처 좌표 자동 생성**으로 얻는다. `setupTexGen()`:

```c
GLfloat plane[4] = { lx, ly, lz, 0.0f };          // 평면식 = 광원 방향
glTexGeni(GL_S, GL_TEXTURE_GEN_MODE, GL_OBJECT_LINEAR);
glTexGenfv(GL_S, GL_OBJECT_PLANE, plane);
glEnable(GL_TEXTURE_GEN_S);
```

`GL_OBJECT_LINEAR` 모드는 각 정점마다 `s = dot(vertex, plane)` 를 자동 계산한다. 여기서 결정적 전제는 **원점 중심의 단위 구(unit sphere)에서는 정점 위치 벡터가 곧 그 지점의 법선**이라는 것이다. 따라서:

```
s = dot(vertexPos, lightDir) ≈ dot(N, L) = N·L
```

즉 GPU 하드웨어의 텍스처 좌표 생성기가 정점별 확산광을 대신 계산해준다.

이어서 `N·L`의 범위 `[-1, 1]`을 텍스처 좌표 `[0, 1]`로 옮겨야 한다. **텍스처 행렬**로 처리한다:

```c
glMatrixMode(GL_TEXTURE);
glLoadIdentity();
glTranslatef(0.5f, 0.0f, 0.0f);   // + 0.5
glScalef(0.5f, 1.0f, 1.0f);       // × 0.5   →  s' = s*0.5 + 0.5
```

결과적으로 정점의 `N·L`이 램프 텍스처의 U좌표가 되어, 밝은 쪽은 램프 오른쪽(하이라이트), 어두운 쪽은 램프 왼쪽(그림자)을 참조한다.

### 2.3 Texture Blending — GL_MODULATE

생성된 램프는 **흑백(회색조)** 이다. 여기에 재질 색을 입히는 단계가 텍스처 환경(Texture Environment) 블렌딩이다. `drawToonSphere()`:

```c
glTexEnvi(GL_TEXTURE_ENV, GL_TEXTURE_ENV_MODE, GL_MODULATE);
glDisable(GL_LIGHTING);
glColor3f(0.85f, 0.35f, 0.25f);   // 기본 재질색(따뜻한 주황빛)
```

`GL_MODULATE`의 블렌딩 식은 **곱셈**이다:

```
finalColor = textureColor × primaryColor(glColor)
```

- `textureColor` = 램프에서 조회한 회색조 밝기(예: 어두운 밴드 80/255 ≈ 0.31)
- `primaryColor` = `glColor3f`로 지정한 재질색 (0.85, 0.35, 0.25)

따라서 어두운 밴드에서는 재질색이 어둡게(그림자), 밝은 밴드에서는 재질색이 밝게(하이라이트) 나타난다. **밝기(램프)와 색상(재질)을 분리**해, 하나의 회색 램프로 어떤 색 물체든 카툰 셰이딩할 수 있는 구조다.

> 참고로 텍스처 환경 모드에는 `REPLACE`(텍스처로 완전 대체), `DECAL`, `ADD`(가산), `BLEND` 등이 있다. 카툰 명암처럼 "밝기 × 색"이 필요한 경우 곱셈인 `MODULATE`가 정답이다. 또한 `drawToonSphere()`에서 `glDisable(GL_LIGHTING)` 으로 GL 기본 조명을 꺼두는데, 조명 계산을 램프가 전담하므로 GL 조명이 개입하면 이중 계산이 되기 때문이다.

## 3. Back-Face Outline의 원리

카툰 렌더링의 검은 외곽선은 **뒷면 셸(shell) 확대 렌더링**, 흔히 "Inverted Hull(뒤집힌 껍질)" 기법으로 만든다. `drawOutline()`:

```c
glEnable(GL_CULL_FACE);
glCullFace(GL_FRONT);          // 앞면을 컬링 → 뒷면만 그림

glDisable(GL_TEXTURE_1D);
glDisable(GL_LIGHTING);
glColor3f(0.0f, 0.0f, 0.0f);   // 순수 검정

glPushMatrix();
glScalef(g_outlineScale, g_outlineScale, g_outlineScale);  // 1.04배 확대
glutSolidSphere(1.0, 64, 64);
glPopMatrix();

glCullFace(GL_BACK);           // 원복
```

### 3.1 두 번의 렌더 패스

`drawToonSphere()`의 그리기 순서가 핵심이다:

1. **외곽선 패스** — 구를 `1.04`배로 살짝 키우고, `glCullFace(GL_FRONT)`로 **앞면을 버려 뒷면만** 검게 그린다.
2. **본체 패스** — 원래 크기(1.0배)로, `glCullFace(GL_BACK)`로 정상적으로 앞면 카툰 셰이딩을 그린다.

### 3.2 왜 외곽선만 보이는가

핵심은 깊이 판정(Depth Test)과 크기 차이의 상호작용이다.

- 확대된 검은 셸의 **뒷면**은 물체 뒤쪽 반구다. 그런데 그 앞에 원래 크기의 본체가 그려지면서, 화면 **중앙부에서는 본체(앞면)가 검은 뒷면보다 카메라에 가까워** 깊이 테스트로 검은색을 가린다.
- 오직 **실루엣 가장자리(rim)** 에서만 확대된 셸이 본체의 윤곽선 밖으로 비어져 나온다. 이 삐져나온 4% 테두리가 곧 검은 외곽선으로 보인다.

`glCullFace(GL_FRONT)`로 뒷면만 그리는 이유는, 확대한 셸의 앞면까지 그리면 물체 정면을 검게 덮어버리기 때문이다. 뒷면만 남기면 물체에 가려지지 않은 테두리만 안전하게 노출된다.

### 3.3 외곽선 두께 제어

외곽선 두께는 확대 배율로 결정된다. `specialKeys()`의 Up/Down 키가 `g_outlineScale`을 조절하며, 하한을 `1.0`으로 막아(음수 두께 방지) 최소 본체 크기 이하로는 내려가지 않게 한다.

> **한계 및 대안:** 이 셸 스케일 방식은 원점 중심의 볼록한(convex) 물체에는 잘 맞지만, 원점이 중심이 아니거나 오목한 물체에서는 외곽선 두께가 균일하지 않게 나온다. 더 견고한 방식은 각 정점을 **법선 방향으로 밀어내는(offset along normal)** 방법이나, 후처리 단계에서 깊이·법선 버퍼의 에지를 검출(Sobel 등)하는 방법이지만, 이는 셰이더나 다중 렌더 타깃이 필요해 고정 파이프라인의 범위를 벗어난다.

# Part II. 형상·외형·변환 관심사 분리 — 튜터링 커리큘럼

> **For agentic workers:** 자기주도 학습(튜터링) 모드. 서브에이전트가 대신 구현하지 않는다. 학습자가 각 Phase 코드를 직접 작성하고, 막힐 때만 `<details>`를 편다. 체크박스(`- [ ]`)로 추적.
>
> **Goal:** 케로로 각 파트의 `Draw()`에 뒤섞인 **형상(Geometry)·외형(Appearance)·변환(Transform)** 을 관심사별로 분리한다. **화면은 그대로 두고(behavior-preserving) 구조만 가른다.** 툰/아웃라인은 이 분리가 끝난 뒤 Part III에서 새 Technique로 얹는다.
>
> **Architecture (SGI Performer / Quake3 계보):**
> - **형상(Geometry)** = 데이터. `Submit()` — 정점만 제출(gluSphere / emit 루프). 상태·변환·텍스처 금지.
> - **외형(Appearance)** = `Material`(데이터, ResourceManagement/app 소유) + `ITechnique`(실행자, `Bind/Unbind`). "Material은 데이터, Technique는 셰이더 대체물".
> - **변환·오케스트레이션** = `Renderer`가 `modelMatrix` 적용 + Technique 순회.
> - 세 데이터는 이미 각자 자리에 있다(형상=메쉬/quadric, 외형=텍스처/UV/색, 변환=`TransformValue`). 리팩터의 일은 **각 데이터를 조작하는 코드**를 `Submit`/`Technique`/`Renderer`로 갈라내는 것.
>
> **Tech Stack:** OpenGL 2.1 고정 파이프라인, GLUT, glm, C++17, CMake(`ninja`).

## 이 커리큘럼 사용법

- 각 Phase: **① 목표 · ② 선행 확인 · ③ 인터페이스(계약 제공) · ④ 구현 유도(질문+함정) · ⑤ 검증 · ⑥ 커밋**.
- **인터페이스(③)는 정답을 준다.** **구현 본문(④)은 당신이 채운다** — 힌트는 접혀 있다.
- **철칙:** 모든 Phase는 **화면이 이전과 100% 동일**해야 성공(behavior-preserving 리팩터). 시각 변화 = 회귀 = 실패.
- 빌드/실행:
  ```bash
  cmake --preset ninja && cmake --build --preset ninja
  ./build_ninja/bin/OpenGL-ComputerGraphics
  ```

## Phase S0 — 이음새(seam) 설계 ★

**① 목표:** 세 관심사의 경계를 종이 위에서 확정한다(코드 최소).

**② 선행 확인:** [KeroroHead::Draw](../../src/model_imp.h#L91)의 각 줄을 **형상/외형/변환** 3색으로 직접 분류해보라. 하나도 애매하지 않게 100% 분류되면 준비 완료.

**③ 인터페이스 (계약):**
```cpp
// 형상: 정점만
struct IGeometry { virtual void Submit() const = 0; };

// 외형-데이터 (Technique가 읽음). UV는 코드 주석대로 여기로 이관.
struct Material {
    Texture*  albedo = nullptr;
    UVValue   uv;
    glm::vec3 baseColor{1,1,1};
    ITechnique* technique = nullptr;   // "어떤 셰이더(전략)로 그릴지"
};

// 외형-실행 (전략): 상태 조작
struct ITechnique {
    virtual ~ITechnique() = default;
    virtual void Bind(const Material&) = 0;
    virtual void Unbind() = 0;
};
// 변환: Model의 TransformValue/modelMatrix 유지, 적용은 Renderer로 이동
```

**④ 구현 유도:** 아래 표를 스스로 완성하라(현재 Draw의 각 줄 → 이사 갈 곳).

| 현재 KeroroHead::Draw | 관심사 | 이사 갈 곳 |
|---|---|---|
| `glPushMatrix; glMultMatrixf(modelMatrix)` | 변환 | Renderer |
| `glEnable(GL_TEXTURE_2D); glBindTexture; GL_TEXTURE 행렬; glColor` | 외형 | TexturedTechnique.Bind |
| `gluSphere(...)` | 형상 | Geometry.Submit |
| `GL_TEXTURE pop; glDisable` | 외형 | TexturedTechnique.Unbind |

- 유도 질문: UV는 형상인가 외형인가? ([transformable.h#L18](../../src/transformable.h#L18) 주석 힌트: "Material 모듈 도입 전까지 여기서 보유" → **외형(Material)** 으로 간다.)

**⑤ 검증:** 코드 없음. 위 분류가 100% 명확하면 통과.

**⑥ 커밋:** 문서만(선택).

## Phase S1 — 형상만 남기기: `Submit()` (Head 파일럿) ★★

**① 목표:** "형상 = 정점 제출"을 `Submit()`으로 격리. 나머지(외형·변환)는 아직 `Draw`에 남겨 **화면 불변** 유지.

**② 선행 확인:** [ParametricGeometry::Draw](../../src/model.cpp#L140)의 emit 루프는 이미 "형상 제출"에 가깝다. quadric 파트의 형상 제출은 몇 줄인가? (gluSphere 한 줄)

**③ 인터페이스:**
```cpp
// Model (또는 각 파트)에 추가
virtual void Submit() const;   // 정점 제출만: gluSphere / emit 루프.
                               // push/pop·glEnable·텍스처·glColor 전부 금지.
```

**④ 구현 유도:**
- `KeroroHead::Submit()` = `gluSphere(quadric, radius, slices, stacks);` **딱 이것만.**
- `Draw()`는 이번엔 **유지**하되, 내부의 `gluSphere(...)` 호출을 `Submit();` 호출로 교체하라. 텍스처/색/변환은 아직 Draw에 그대로. → 화면 불변.
- 함정:
  - `Submit`에 `glPushMatrix`나 `glColor`를 넣지 마라 — 그건 S2/S3 몫. Submit이 "순수한지"가 이 Phase의 전부다.
  - `gluSphere`는 `const` 메서드에서도 호출 가능하나 `quadric` 멤버가 `const`서 접근되는지 확인(필요 시 `mutable` 또는 `Submit()` 비-const로).

**⑤ 검증:** 빌드+실행 → Head 그대로. `Submit()`을 눈으로 재검토 — 형상 외 아무것도 안 하면 통과.

**⑥ 커밋:** `git commit -m "[refactor] 형상 제출 Submit() 분리 (Head 파일럿)"`

## Phase S2 — 외형 분리: Material(데이터) + Technique(실행) ★★★

**① 목표:** Head의 텍스처·UV·색을 `Material` **데이터**와 `TexturedTechnique` **실행자**로 추출. Draw는 `Bind → Submit → Unbind`로 축약.

**② 선행 확인:** Draw의 어느 줄들이 "상태를 켜고", 어느 줄들이 "끄나"? **Bind/Unbind 쌍**으로 묶어보라.

**③ 인터페이스 (`src/material.h` 신규):**
```cpp
struct Material {                       // 데이터 (self-execute 안 함)
    Texture*  albedo = nullptr;
    UVValue   uv;
    glm::vec3 baseColor{1.0f,1.0f,1.0f};
    ITechnique* technique = nullptr;
};

struct ITechnique {                     // 전략 실행자
    virtual ~ITechnique() = default;
    virtual void Bind(const Material&) = 0;
    virtual void Unbind() = 0;
};

class TexturedTechnique : public ITechnique {  // 텍스처+UV행렬+색
  public:
    void Bind(const Material&) override;
    void Unbind() override;
};

class AlphaTestTechnique : public TexturedTechnique {  // Hat용: 알파테스트 추가
  public:
    void Bind(const Material&) override;   // TexturedTechnique::Bind 후 glEnable(GL_ALPHA_TEST)
    void Unbind() override;                // glDisable(GL_ALPHA_TEST) 후 상위 Unbind
};
```

**④ 구현 유도:**
- `TexturedTechnique::Bind` = [KeroroHead::Draw#L98-L112](../../src/model_imp.h#L98-L112)의 텍스처 enable/bind/UV 행렬/`glColor`. `Unbind` = [#L121-L127](../../src/model_imp.h#L121-L127).
- Head는 이제 `Material`(albedo=texture, uv, baseColor, technique=&textured)을 **참조**하고, Draw는:
  ```cpp
  material->technique->Bind(*material);
  Submit();
  material->technique->Unbind();
  ```
- `IUVTransformable`은 `KeroroHead::uv` 대신 **Material.uv**를 읽고 쓰게 위임(멤버 이관).
- 소유권: **Material 데이터는 ResourceManagement(또는 app)** 이 소유, **Technique 인스턴스는 작은 라이브러리/app** 이 소유해 여러 파트가 **공유**(엔진 계보: Material=데이터, Technique=셰이더 대체물).
- 함정:
  - Bind가 `GL_TEXTURE` 행렬을 push하면 Unbind가 반드시 pop. 짝이 안 맞으면 다음 파트 오염.
  - AlphaTestTechnique은 `TexturedTechnique`를 재사용(상속 or 합성) — 알파테스트만 추가.

**⑤ 검증:** Head(그리고 Hat) 화면 불변. **같은 `TexturedTechnique` 인스턴스를 Body에도** 물려 공유가 되는지 확인(데이터/실행 분리의 이점 체감).

**⑥ 커밋:** `git commit -m "[refactor] 외형 분리 — Material 데이터 + Textured/AlphaTest Technique"`

## Phase S3 — 변환·오케스트레이션 분리: Renderer (Draw 제거) ★★★

**① 목표:** 변환 적용(TRS)과 패스 순회를 `Renderer`로 올린다. 파트의 `Draw()`를 **없앤다.**

**② 선행 확인:** [Renderer::Render](../../src/renderer.cpp#L14-L20)는 지금 `model->Draw()`만 부른다. 여기가 오케스트레이터가 될 자리다.

**③ 인터페이스:**
```cpp
// Model 노출: GetModelMatrix()(이미 있음) + Submit() + GetMaterial()
void Renderer::Render(Camera& camera) {
    for (auto& m : models) {
        glPushMatrix();
        glMultMatrixf(glm::value_ptr(m->GetModelMatrix()));   // 변환
        Material* mat = m->GetMaterial();
        if (mat && mat->technique) {
            mat->technique->Bind(*mat);
            m->Submit();                                      // 형상
            mat->technique->Unbind();
        } else {
            m->Submit();
        }
        glPopMatrix();
    }
}
```

**④ 구현 유도:**
- 각 파트 `Draw()`에 남아 있던 `glPushMatrix/glMultMatrix/glPopMatrix`(변환)와 `Bind/Unbind` 호출을 **Renderer로 올리고**, `Draw()`를 삭제.
- Model에 `Material* GetMaterial()` 추가(S2에서 만든 material 참조 반환).
- 함정:
  - **텍스처 행렬(GL_TEXTURE) push/pop은 Technique 책임**, Renderer는 `GL_MODELVIEW`만 만진다. 섞지 마라.
  - `ParametricGeometry`(Body/Hat)는 [Draw](../../src/model.cpp#L140)가 push/pop+emit을 함께 한다 → S1에서 뺀 `Submit()`(emit만)을 Renderer가 변환으로 감싸도록 정리.

**⑤ 검증:** 전 파트가 Renderer 경유로 **여전히 동일**. `Draw()`가 다 지워졌는데 화면이 같으면 삼분할 완성.

**⑥ 커밋:** `git commit -m "[refactor] Renderer가 변환+Technique 오케스트레이션, 파트 Draw() 제거"`

struct LightValue
{
    LightType type = LightType::Directional;

**④ 구현 유도:**

  - 유도 질문: 모델의 회전이 `R`이라면, 월드→오브젝트로 방향 벡터를 옮기는 변환은? (힌트: 방향에는 이동이 안 붙는다. 회전의 역 = 직교행렬이면 전치)
  - 함정: `modelMatrix`에는 T·R·S가 다 섞여 있다. 방향 벡터엔 `mat3(inverse(modelMatrix))`의 전치를 쓰거나, 회전만 뽑아 역을 취하라. 비균일 스케일이 있으면 **역전치(normal matrix)** 가 정석.

<details><summary>막히면: 방향 변환 한 줄</summary>

```cpp
// 방향 벡터의 월드→오브젝트: normal matrix의 역 개념
glm::mat3 objFromWorld = glm::transpose(glm::mat3(modelMatrix)); // R가 직교면 R^-1 = R^T
glm::vec3 Lobj = glm::normalize(objFromWorld * (-keyLight.direction));
```

</details>

- **Spot 표준 경로**(GL 고정 조명)도 이번에 추가: `ApplyPointLight` 패턴을 본떠 `GL_SPOT_CUTOFF`/`GL_SPOT_DIRECTION`/`GL_SPOT_EXPONENT`를 세팅하는 경로를 만들어라(툰과 별개, 비교용).

## Phase 3 — GL_NORMAL_MAP texgen 최소 검증 ★★★

**① 학습 목표:** `gluSphere`를 유지한 채, `GL_NORMAL_MAP` texgen + 텍스처 행렬로 `N·L`을 1D 램프 좌표로 만드는 **메커니즘을 최소 코드로 먼저 증명**한다. (macOS 드라이버에서 도는지 확인하는 게 목적 — 이후 전부가 여기 얹힌다.)

**② 선행 확인:**
- chapter7의 `GL_OBJECT_LINEAR`(위치 기반)은 왜 구에서만 되나? `GL_NORMAL_MAP`(법선 기반)은 왜 원기둥에도 되나?
- 텍스처 행렬은 texgen이 만든 좌표에 **곱해진다.** `NORMAL_MAP`이 `(s,t,r)=N`을 주면, 행렬 1행을 광원방향 `L`로 두면 `s' = L·N = N·L`이 된다 — 스스로 유도해보라.
- `NORMAL_MAP`이 만드는 법선은 **눈(eye) 공간**이다. 그럼 `L`은 어느 공간이어야 하나?

**③ 인터페이스 (별도 최소 테스트 — chapter7 복제본이나 임시 함수):**
```cpp
// 1D 램프를 s = N·L 로 조회하도록 texgen + 텍스처 행렬 세팅
void SetupNormalMapRamp(const glm::vec3 &lightDirEye); // 눈공간 광원방향
```

**④ 구현 유도:**
- texgen: `GL_S/GL_T/GL_R` **세 좌표 모두** `GL_NORMAL_MAP`으로 켜라.
  - 유도 질문: 왜 S 하나가 아니라 S·T·R 셋 다인가? (힌트: `NORMAL_MAP`은 좌표별로 법선의 **해당 성분**만 준다 — S→Nx, T→Ny, R→Nz. 셋을 다 켜야 행렬이 `N` 전체를 볼 수 있다.)
- 텍스처 행렬: 1행이 `N`을 `L`에 투영 + `*0.5+0.5` remap을 동시에 하도록 구성.

<details><summary>막히면: 텍스처 행렬 1행 구성</summary>

최종 `s = 0.5*(N·L) + 0.5`를 원한다. 생성 좌표가 `(Nx,Ny,Nz,1)`이므로 1행 = `(0.5*Lx, 0.5*Ly, 0.5*Lz, 0.5)`. T·R 행은 1D에서 안 쓰이니 무해하게, 4행 `q=(0,0,0,1)`. **주의: GL 행렬은 열 우선(column-major)** — `glLoadMatrixf`에 넣을 때 전치에 유의.
</details>

- 눈공간 `L`: `lightDirEye = normalize(mat3(viewMatrix) * (-keyLight.direction))`. (뷰 행렬만 곱한다 — 모델과 무관.)
- 함정:
  - S만 켜면 `s=Nx`만 나와 행렬을 곱해도 `N·L`이 안 된다(위 유도 질문).
  - `L`을 오브젝트 공간으로 넣으면 틀린다 — `NORMAL_MAP`은 눈공간 법선이다.
  - `GL_NORMALIZE`가 켜져 있어야 스케일된 모델의 법선이 정규화된다([이미 Lighting.Init에서 enable](../../src/lighting.cpp#L24)).

**⑤ 디버그 시각화:** `gluSphere` 하나에 이 세팅 + 회색 램프 → **밴드 명암**이 보이면 성공. `lightDirEye`를 좌우로 돌려 밴드 경계가 미끄러지는지 확인. 그다음 **`gluCylinder`로 바꿔** 원기둥에서도 밴드가 옆면을 감싸면 — 이 방식이 quadric 전반에 통함이 증명된 것(스피어 트릭과의 결정적 차이).
- 실패 시: 전체 단색 → 텍스처 행렬 전치/열우선 실수 또는 S만 켠 것.

**⑥ 커밋:** `git commit -m "[test] GL_NORMAL_MAP texgen + 텍스처행렬로 N·L 램프 검증"`

**② 선행 확인:**
- `H = normalize(L + V)`. 눈공간에서 `V`는 대략 무엇인가? (방향성 근사: `(0,0,1)`)
- 왜 `(N·H)^shininess`를 계산 안 하고 **램프 모양**으로 대체할 수 있나? (LUT가 임계·급경사를 그대로 담음)

**③ 인터페이스:**
```cpp
void BuildSpecularRamp(float edge); // t가 edge 부근서 급격히 흰색 (경성 스텝)
// Begin: 유닛A(diffuse, 행1=L) + 유닛B(specular, 행1=H) 둘 다 NORMAL_MAP
```

**④ 구현 유도:**
- 유닛 배치: diffuse 유닛은 `MODULATE`(밝기×baseColor), specular 유닛은 그 위에 `GL_ADD`(가산). 유닛 수가 부족하면 **멀티패스**(본체 그린 뒤 스페큘러만 가산 블렌드로 재드로우).
- `H` 세팅: `H_eye = normalize(ctx.lightDirEye + ctx.viewDirEye)`, 이걸 스페큘러 유닛의 텍스처 행렬 1행에 넣어라(`*0.5+0.5` 없이 0..1 클램프는 LUT/wrap이 담당).
- 함정:
  - 스페큘러가 표면 전체를 덮음 → `edge`를 1.0 가까이. 램프 최상단만 흰색.
  - 각지게 튐 → quadric `slices/stacks`가 낮음(KeroroHat이 uRes 64인 [이유](../../src/model_imp.h#L225)와 동일). 스페큘러 파트만 stacks를 올려라.
  - `N·H`가 음수인 뒷면 → `GL_CLAMP_TO_EDGE`로 램프[0](검정) 참조되게.

**⑤ 디버그 시각화:** 디퓨즈 off, 스페큘러만 → 광원 쪽 표면에 **작고 뚜렷한 흰 점**. 카메라를 돌리면 점이 미끄러지면 `V` 의존성 정상.

**⑥ 커밋:** `git commit -m "[feat] Specular 램프(NORMAL_MAP + H) + 툰 하이라이트"`

## Phase 6 — 셸-스케일 아웃라인 ★★

**① 학습 목표:** Part I의 Inverted Hull(뒷면 셸 확대)을 케로로 quadric에 적용한다. 구·원기둥은 볼록(convex)이라 셸 스케일로 충분하다(방안 A 선택).

**② 선행 확인:**
- Part I 3.1~3.2: 왜 앞면을 컬링하고 뒷면만 그리나? 왜 확대해야 테두리만 보이나?
- 셸 스케일의 한계(비대칭 TRS 스케일 파트에서 두께 불균일)를 어디까지 감수할지 스스로 정하라.

**③ 인터페이스:**
```cpp
// 각 파트 Draw가 본체 전에 확대·검정·앞면컬링으로 같은 quadric을 한 번 더 그림
// (공통화하려면) void DrawOutlineShell(float scale, const std::function<void()>& drawGeom);
```

**④ 구현 유도:**
- Part I의 `drawOutline`을 그대로 이식: `glCullFace(GL_FRONT)`, 조명/텍스처 off, `glColor3f(0,0,0)`, `glScalef(scale,scale,scale)` 후 **같은 quadric 도형**을 그림, 끝에 `glCullFace(GL_BACK)` 복원.
- 순서: **아웃라인(확대·뒷면) → 본체(정상·앞면)**.
- 함정:
  - `GL_CULL_FACE`는 [앱 전역 enable](../../apps/main.cpp#L296) — `cullFace` 방향만 토글.
  - 원기둥 아웃라인은 스케일 시 길이도 늘어 캡이 벌어짐 → `scale`을 작게(1.03 근처).
  - 발(scale `0.11,0.06,0.15`)에서 두께 불균일이 보이면, 그 파트만 눈공간 오프셋으로 보정(선택 심화).

**⑤ 디버그 시각화:** `scale`을 1.1로 과장 → 검은 셸 확인, 1.03 근처로 조임. 회전시켜도 실루엣을 따라 테두리가 유지되면 정상.

**⑥ 커밋:** `git commit -m "[feat] 셸-스케일 아웃라인(Inverted Hull)"`

## Phase 7 — 방향광 밴드 + 점/스팟 표준광 ★★★★

**① 학습 목표:** `NORMAL_MAP`+상수 텍스처 행렬 방식의 **구조적 경계**를 이해하고, 점광/스팟을 올바른 방법으로 처리한다.

**② 선행 확인 (핵심 통찰):**
- 텍스처 행렬은 **한 Draw 동안 모든 정점에 동일**하다. 방향광은 `L`이 상수라 문제없다. 그런데 점광의 `L`은 **정점마다 다르다**. 상수 행렬로 정점별 `L`을 표현할 수 있나? (답: 없다 — 이게 texgen 툰 방식의 구조적 한계다.)

**③ 결론 및 인터페이스:**
```cpp
// 밴드(툰 계단) = 방향성 주광(sun) 하나만 담당 → texgen 행렬 = L_key
// 점광/스팟 = 표준 GL 조명으로 은은한 fill (밴드화하지 않음)
```

**④ 구현 유도:**
- 밴드: P4의 방향광 세팅 유지(주광 = sun).
- 점광/스팟: [Lighting](../../src/lighting.h#L38)의 표준 GL 경로(P2에서 만든 spot 포함)를 살린다. 툰 패스는 조명을 껐으므로(`glDisable(GL_LIGHTING)`) 대안 둘 중 택1:
  - (a) 점광/스팟용 **별도 가산 패스**: 조명 on + 어두운 재질로 한 번 더 그려 fill 라이트를 더한다.
  - (b) 점광 영향을 **약한 2번째 램프**로 근사(방향 근사). 정밀하진 않지만 툰 느낌 유지.
- 유도 질문: 설계 D5("밴드는 주광 1개")가 왜 여기서 코드로 강제되는지 이제 이해됐을 것이다 — 스스로 서술해보라.
- 함정: 점광을 억지로 밴드화하려고 정점마다 행렬을 바꾸면 Draw가 정점 단위로 쪼개져 성능·구조가 무너진다. 하지 마라.

**⑤ 디버그 시각화:** sun을 돌리면 밴드가 이동, 점광을 움직이면 **밴드가 아니라 부드러운 fill**이 따라오는지 확인. 스팟은 콘 경계가 표준 조명으로 나타나면 정상.

**⑥ 커밋:** `git commit -m "[feat] 방향광 밴드 + 점/스팟 표준 fill 라이트"`

## Phase 8 — 케로로 전신 통합 + ImGui 토글 ★★★

**① 학습 목표:** 모든 파트에 Material을 연결하고, 런타임에 **일반↔툰 전환**을 UI로 붙인다.

**② 선행 확인:** [HandleDisplayEvent](../../apps/main.cpp#L277)의 렌더 순서와, [UITransformPanel/UILightingPanel](../../apps/main.cpp#L330) 패턴을 확인하라.

**③ 인터페이스:** 앱이 `ToonMaterial` 인스턴스를 소유하고 각 모델에 `SetMaterial`. UI는 램프 밴드 수·아웃라인 두께·툰 on/off를 조절.

**④ 구현 유도:**
- 모든 quadric 파트(Head/Arm/Leg/Foot/Hand)에 `SetMaterial`로 툰을 연결한다. **파라메트릭 이관이 필요 없다** — Hand(캡슐)도 `gluQuadricNormals`가 법선을 주므로 NORMAL_MAP이 그대로 작동한다.
- 툴바 토글: `bool g_toonEnabled`로 `SetMaterial(nullptr)` ↔ `SetMaterial(&toon)` 스왑. 이게 **런타임 폴리모피즘의 정당한 사례**(D 설계판단)임을 스스로 확인.
- 함정: 스카이박스/땅은 툰 대상이 아님 — 이들엔 Material을 붙이지 말 것. Material의 `End`가 GL 상태를 확실히 복원하는지 다시 점검(안 그러면 배경이 오염됨).

**⑤ 검증(전체):** 툰 on → 케로로 전신이 밴드 명암 + 검은 아웃라인 + 스페큘러 점. 광원(sun/point/spot)을 돌리면 반응. 툰 off → 기존 GL 셰이딩으로 즉시 복귀. 스카이박스/땅은 무영향.

**⑥ 커밋:** `git commit -m "[feat] 케로로 전신 툰 셰이딩 통합 + ImGui 토글"`
